## 1. Goal

A private, single-user, native SwiftUI iPhone app that keeps the web app's curated workout-tracking
experience (feature complete, Eric-designed, "awesome") and adds what a PWA cannot do on the
**iPhone Duo**: a real sidebar on the inner display, split layouts, Live Activity + Dynamic Island
for the rest timer, notifications, haptics. Parity is the floor. Not goals: App Store release,
other users, iPad/Mac, widgets, Shortcuts, Control Center, HealthKit/Apple Fitness (Eric starts
his Fitness workouts in Apple's app himself and likes it that way), Apple Watch, the web app.
Also out: multi-window and keyboard shortcuts (one scene; no `UIApplicationSupportsMultipleScenes`).

## 2. Decisions (settled; see `AGENTS.md` → Product decisions for the ones made earlier)

Eric deferred the technical choices to Claude. These close every item in `docs/port/OPEN-QUESTIONS.md`.

**Data and sync**
- SwiftData + CloudKit private database. Container `iCloud.com.ericribeiro.Workouts`. Until the
  Developer Program is approved, the store runs with CloudKit **off** behind one flag
  (`ModelConfiguration(cloudKitDatabase: .none)`); the schema is written CloudKit-safe from day one.
- Settings live outside SwiftData, in a `SettingsStore` with two backends sharing one key list and
  one test. **`UserDefaults` is the runtime backend until the iCloud key-value entitlement exists
  (phase 7)**; the `NSUbiquitousKeyValueStore` backend (syncs, cannot produce duplicate rows) is
  selected by the same `cloudKit` flag as the container, in task 7.3. Keys: `defaultUnit`,
  `defaultRestSeconds` (90), `weeklyGoal` (3), `e1rmFormula` (epley), `restPresets`,
  `keepScreenOn` (true), `downloadAllVideos` (false). Appearance follows the system.
- Library: 1,038 exercises bundled as `library.json` + thumbnails, generated by
  `scripts/build-library` from the snapshot (section 4). Seeded on first launch, re-seeded by
  upsert when `libraryVersion` in the JSON is newer than the stored one; never touches custom
  exercises, overrides or sticky notes; retires what left. Media: `docs/port/media.md`.
- One-time history migration from the web Postgres: an **Import** action in Settings that reads a
  JSON export (produced later by a script against the web DB) through the normal SwiftData path,
  so it syncs. Exercise ids match because both sides use UUIDv5(source, sourceId); the namespace
  is copied from the web's `store.ExerciseID` when the import script is written (task 7.4).
- Custom exercise: deletable when no history references it, otherwise "Archive" (= retire).

**Navigation and layout**
- `TabView` with `.tabViewStyle(.sidebarAdaptable)` and `.defaultAdaptableTabBarPlacement(.sidebar)`.
  Three top-level `Tab`s in the web's order, **History · Workout · Exercises**; **Workout is the
  default selection**. One `TabSection` per **folder**, header = folder name, children = that
  folder's templates as `Tab`s with `.tabPlacement(.sidebarOnly)` (never in the compact bar), each
  rendering the template preview with Start / Edit; `.sectionActions` carries "New Template": one-tap
  access to any template on the inner display. Where the system places the bar is not assumed.
- **Settings** is a gear `toolbar` button on the Workout tab, and `tabViewSidebarBottomBar` on
  regular width, presenting a `Form` sheet. No fourth tab.
- Exercises and History use `NavigationSplitView` with `navigationSplitViewColumnWidth(min:ideal:max:)`
  so the detail keeps at least 420 pt beside an open sidebar (compact → push). The Workout tab is a
  single column in both widths, since the sidebar already lists templates: the web's **card grid**
  (2 columns compact, 3 regular, collapsible folders). The template preview stays a
  medium-detent sheet (the web's best interaction).
- **Active workout**: one presentation in both widths, a `fullScreenCover` on the root `TabView`,
  not tied to any tab, as the web's full-screen layer. Inside it the layout follows
  `horizontalSizeClass`: compact → the set table; regular → `HStack` set table | exercise pane
  (video, instructions, Previous, records, sticky note) following the focused exercise (the web's
  `PLAN.md:204` idea). Folding only changes the size class inside the cover, so draft, focus and
  scroll are untouched. Minimise dismisses the cover; the bottom accessory (and Live Activity)
  restore it, and a running workout survives any tab change.
- Minimised workout: `.tabViewBottomAccessory` (the system mini-player slot above the tab bar; it
  adapts to the sidebar). It reads `tabViewBottomAccessoryPlacement`: `.expanded` shows name ·
  elapsed · rest countdown · Skip; `.inline` only the countdown (or elapsed). Tap restores.
  History and Exercises lists set `tabBarMinimizeBehavior(.onScrollDown)` (not Apple's
  `toolbarMinimizeBehavior`: absent from the 27.2 interface).
- `AppNavigation` (@Observable) with typed routes, so Live Activity buttons and notification
  actions can open the logging screen or a template. App Intents exist only as the mechanism
  behind those buttons; nothing is exposed to Shortcuts or Spotlight.

**Active workout behaviour**
- Start from a template or **Empty Workout** (name "Workout"). Exactly one in progress.
- Web rules kept verbatim (`docs/port/screens/active-workout.md`): check → rest starts, presets
  0:30/1:00/2:00/3:00 + up to 6 customs, ±10 s adjust, empty sets cannot be checked, Finish
  dialogs, Discard confirmation, Previous autofill, warm-up ramp, supersets numbering. Superset
  rest starts on every check (web behaviour). No RPE UI (field kept in the model).
- Finish summary adds a **PR count** (native improvement; `prsInSession` already exists).
- Rest end: local notification, interruption level `.timeSensitive`, body "Rest over · Set 3 ·
  27.5 lb × 8" (next set included), actions **Skip** and **+30 s**. In foreground the
  `UNUserNotificationCenterDelegate` returns `[]` from `willPresent` and the app plays haptic + flash.
- Timer correctness: render with `Text(timerInterval:)` from `restEndsAt`; never a counter. Rest
  state is persisted on the in-progress `Workout` as optional `restEndsAt`, `restSeconds`,
  `restSetID` (CloudKit-safe, cleared on end), so a relaunch resumes a running rest.
- Rest UI: a `safeAreaBar(edge: .bottom)` (system glass; stacks with the keyboard) with the
  countdown and −10 s / +10 s / Skip as `.buttonStyle(.glass)`; the header keeps the web's timer
  button (idle: stopwatch; running: countdown) as a `ToolbarItem`.
- Keyboard: system `.decimalPad` with a keyboard `ToolbarItemGroup` (−step, +step, Previous,
  Done) and a Next that advances weight → reps → next row; steps from the web
  (`docs/port/screens/active-workout.md`). The keyboard covers half the closed screen, so Next is
  the mitigation; custom keypad only if this proves worse.
- **SetTable** (`Workouts/Features/Shared/SetTable`, task 2.1) is one shared component in three
  modes, template / active / past: template editor, logging screen, past-workout editor.
- `isIdleTimerDisabled` while logging when `keepScreenOn`.

**Native layer**
- **Live Activity** (`WorkoutsLiveActivity` extension; `NSSupportsLiveActivities` in Info.plist).
  `ContentState`: exercise name, set index/count, next-set text, `startedAt`, `restEndsAt?`. Lock
  screen + expanded Island: exercise, "Set 3 of 4", rest countdown `Text(timerInterval:)` or elapsed
  `Text(timerInterval: startedAt...distantFuture, countsDown: false)` when no rest runs; buttons
  `Button(intent:)` **Skip** / **+30 s** / **Done set** as `LiveActivityIntent`s that call the
  engine in-process. Compact: leading exercise glyph, trailing countdown text; minimal
  `ProgressView(timerInterval:)` ring. `staleDate = restEndsAt`, `relevanceScore` 1 while resting.
  Request on workout start, update on every check/skip/adjust, `end(dismissalPolicy: .immediate)`
  on Finish/Discard. While the app is suspended it cannot flip to "rest over" (no push server):
  the countdown reaching 0:00 is the only in-Island signal, the local notification the alarm.
  `WorkoutActivityAttributes` lives in `WorkoutsKit`, linked by app and extension.
- **Haptics** via `.sensoryFeedback`: set checked `.impact(weight: .light)`, rest end `.success`,
  PR at finish `.levelChange`, destructive confirm `.warning`, minimise/restore `.selection`.
- **Not built, by decision (2026-11-03)**: widgets, Shortcuts/Siri intents, Spotlight, Control
  Center controls, HealthKit (Eric runs Apple Fitness alongside; a live session needs a Watch app).
- **Liquid Glass**: system bars and controls; no hand-placed `.glassEffect()` unless something
  floats over content (the rest bar is a `safeAreaBar`, not a floating pill);
  `.navigationTransition(.zoom(sourceID:in:))` with `.matchedTransitionSource(id:in:)` on the
  card or row, card → preview sheet and row → detail. Eric's palette becomes semantic
  colours in the asset catalog (accent, ok, danger, warm-up, set-kind colours) with light/dark
  variants; everything else is system material.
- **Accessibility**: every interactive element labelled (agents navigate by the tree too);
  Dynamic Type everywhere; the set table is verified at AX sizes (no clipping): at
  `dynamicTypeSize.isAccessibilitySize` each row becomes a two-line stack via `ViewThatFits`.

**Duo rules (from Apple's app-resizability skill; also in `AGENTS.md`)**
- Size classes only; never `UIScreen.main`, idiom, orientation, or hardcoded sizes. Width can
  change mid-session (fold/unfold) and the app must keep selection, scroll and the active workout.
- Asymmetric safe areas are normal; use `.safeAreaInset`/`.safeAreaPadding`, no magic numbers.
  Observed on Eric's Duo (closed, portrait): the status area is a vertical strip on the trailing
  edge, not a top bar, so trailing-aligned controls sit against it (`docs/port/screenshots/duo-closed-*`).
- All four orientations supported (already in the project). Launch screen generated (already).
- Hinge: `View.onHingeChange` / `DeviceHinge.Status` (`.closed`, `.partiallyOpen`, `.fullyOpen`;
  SwiftUI, iOS 27.1, below our 27.2 target) drive the half-open **bench mode** (task 6.1).
- Verify in four poses on the `iPhone Duo` simulator: closed portrait, closed landscape, open
  tall, open wide (`.claude/skills/verify-ui`).

## 3. Experience, screen by screen (what "awesome" means here)

- **Workout tab**: large title, folder sections with the card grid; cards show the exercise
  summary and "last performed" exactly as the web. Tap → preview sheet (medium detent) with Start.
  On the open Duo the grid is the tab's whole content and the sidebar lists the templates (a
  selected one shows its preview). The editor pushes within the tab; the exercise picker is a sheet.
- **Logging screen**: the web's set table (set · previous · weight · reps · ✓) with the native
  keyboard accessory; checked rows tint; the glass rest bar sits above the keyboard; drag down or
  tap the chevron to minimise. Open Duo: the right pane follows the focused exercise. Half-open
  (propped on the bench): media on the upper half, set table on the lower, split on the hinge.
- **Rest timer**: bar in app, Dynamic Island when away, notification when locked; Skip/+30 s
  everywhere via the same intents.
- **History tab**: weekly goal chart (Swift Charts) → month sections → cards with best sets and
  PR count; detail with PR lines and trophies; edit past workout; calendar sheet. Open Duo: list |
  detail.
- **Exercises tab**: `.searchable` with body-part and equipment scopes, rows with thumbnail +
  latest best set, custom/retired tags; detail with segmented About / History / Charts / Records,
  video loop at the top, sticky note editable here too (native improvement).
- **Settings sheet**: unit, default rest, weekly goal, e1RM formula, keep screen on, download
  all videos, iCloud status line, Import (migration), About (SmartWorkout credit).

## 4. Architecture

```
Workouts.xcodeproj
├─ Workouts/                 app target (SwiftUI shell + features)
│  ├─ App/                   WorkoutsApp, AppNavigation, ModelContainer setup, Settings store
│  ├─ Design/                Colours (asset catalog), typography helpers, rest bar, haptics map
│  ├─ Features/{Shared,Workout,ActiveWorkout,History,Exercises,Settings}/   views + view models (@Observable)
│  └─ Resources/Library/     library.json + thumbs/ (generated, committed; ~25 MB)
├─ WorkoutsLiveActivity/     widget extension holding only the Live Activity
├─ Packages/WorkoutsKit/     platform-free: Model (SwiftData @Model types), Math (done),
│                            Library (seed/upsert), Media (MediaStore), Session (ActiveWorkoutEngine,
│                            RestTimer), Activity (WorkoutActivityAttributes, Live Activity intents)
└─ scripts/build-library     Swift script: snapshot → library.json + thumbs (run on this Mac)
```

- **SwiftData models** (`docs/port/data-model.md`, CloudKit-safe): `Exercise`, `ExerciseOverride`,
  `StickyNote`, `TemplateFolder`, `Template`, `TemplateExercise`, `TemplateSet`, `Workout`,
  `WorkoutExercise`, `WorkoutSet`. All relationships optional with explicit `deleteRule`
  (cascade/nullify; RESTRICT becomes an app check), every stored property defaulted, enums as
  raw strings, `Double` weights, no `.unique`. `LibraryMeta` is a plain `Codable` in `library.json`,
  not a model. `Workout.finishedAt == nil` marks the one in-progress workout; every query
  excludes it (`#Predicate`). Positions are Ints; reorders rewrite them.
- **ActiveWorkoutEngine** (WorkoutsKit, `@Observable`, `@MainActor`): owns the in-progress
  `Workout`, exposes check/uncheck/add/replace/remove/reorder, Previous lookup, warm-up ramp,
  rest timer state (persisted on the `Workout`), finish/discard, and `checkCount` /
  `restEndCount` counters that views turn into `.sensoryFeedback` triggers. Pure logic tested on
  macOS with an in-memory `ModelContainer`. Views read from it; the Live Activity only renders the
  `ContentState` it pushes. `LiveActivityIntent.perform()` runs in the app process, so intents
  call the engine directly (no shared store, no App Group): the intent types sit in `WorkoutsKit`
  so both targets compile them, and reach the engine through a launch-registered dependency.
- **Entitlements**: iCloud (CloudKit and key-value), Push (CloudKit silent), Background Modes
  (remote-notification), `com.apple.developer.usernotifications.time-sensitive` (for
  `.timeSensitive`). **No App Groups**. Added with `xcrun xcodeproj`/`AddEntitlement` once a team
  exists; the Live Activity extension needs only `NSSupportsLiveActivities`.
- **Testing**: `./dev kit` for all WorkoutsKit logic (SwiftData in memory works on macOS);
  `./dev test` for the few app-level tests (navigation model, settings store); UI proof by
  `RenderPreview` and the device-interaction tools; no snapshot-testing dependency.

## 7. Risks and unknowns

- **Hinge APIs are real**: SwiftUI `View.onHingeChange(isEnabled:_:)` with `DeviceHingeContext` /
  `DeviceHinge.Status` (iOS 27.1) and UIKit `UIHinge` / `UIHingeInteraction`, below our 27.2
  target. The simulator's fold is not scriptable (`verify-ui`), so hinge work (6.1) is verified by
  screenshot through Device Hub.
- **Sidebar placement**: `.sidebarAdaptable` defaults to the iPad-style tab bar on regular width
  without `defaultAdaptableTabBarPlacement(.sidebar)`, the bar may be vertical, and template
  `Tab`s without `.tabPlacement(.sidebarOnly)` leak into the compact bar (screenshots in 0.5, 3.6).
- **Live Activity cannot update itself while the app is suspended** (no push server), so it cannot
  flip to "rest over": the countdown hitting 0:00 and the time-sensitive notification are the
  signals. Its intents run in the app process, so the engine must resume the persisted workout first.
- **SwiftData + CloudKit**: no unique constraints, optional relationships, additive-only migrations
  once CloudKit is on; keep `SchemaV1` frozen after 7.2.
- **Island screenshots** need an Island sim (`iPhone 18 Pro`). **Media**: thumbnails are bundled,
  only videos degrade offline. **TestFlight** needs the paid program; until then simulator-only.
- **Budget**: Opus orchestrates from here using this file, Sonnet implements.
