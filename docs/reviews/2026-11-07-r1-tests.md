## P1

### P1-1 `WorkoutDetailSnapshots/loadingAndLoadedShareTheChrome` depends on the simulator: it compares a Liquid Glass toolbar across simulators

`WorkoutsTests/Snapshot/SnapshotWorkoutDetailTests.swift:54` (the `loaded` reference assert).

- **Evidence.** Two worktree clones (`agent-a5eed6fa…`, `agent-a61a7eff…`) wrote `loaded-large-light.actual.png`. Both
  differ from the reference by the same 3,705 pixels (0.125%, above the 0.05% limit). The differing pixels sit in a
  single box, x 219-352 pt, y 35-62 pt. That box is the glass capsule holding the pencil, copy and trash toolbar
  buttons, and nothing else on the page differs. The `loading` image passes on the clones because its bar has no
  toolbar group yet. `assertSameChrome` (line 56) also passes, because it compares two renders on the same simulator.
- **Cause.** The capsule is system Liquid Glass. Its specular edge and shadow come from the simulator's state, not from
  the view. This is most likely the device orientation or hinge pose, or an accessibility display setting that differs
  per clone (glass lighting follows device motion). `Snapshot.frame` pins the color scheme, Dynamic Type and locale, but
  nothing pins the material. The 0.05% budget assumes one simulator (`SnapshotTesting.swift:33-35`), and the `loaded`
  reference breaks that assumption as soon as the pool is used.
- **Fix (one worker task).** Keep the chrome rule as a same-run comparison and stop pixel-comparing glass against a
  file. Add an `excludingTop:`/`mask:` parameter to `Snapshot.assert(png:)` (`SnapshotTesting.swift:80`) that blanks
  the top N points before diffing. Pass `excludingTop: 80` for both `loading` and `loaded` in this test. The chrome stays
  covered by `assertSameChrome` (loading vs loaded, same simulator) and by `FirstFrameUITests`. Re-record the two PNGs.
  Also have `./dev test` assert `closed-portrait` before it runs, the same way `ui-test` does (or call `./dev pose
  closed-portrait`), so no other hosted snapshot inherits a clone's pose. Proof: `./dev test
  SnapshotTests/WorkoutDetailSnapshots` passes on the main sim and on `DEV_SIM='iPhone Duo 2'`.

### P1-2 About 15 absence asserts (`XCTAssertFalse(x.exists)`) pass by default right after an action

The worst ones are `WorkoutsUITests/ResumeControlUITests.swift:14`, `StickyNoteUITests.swift:51,55`,
`LoggingBlockMenuUITests.swift:166`, `FoldersUITests.swift:113,125` and `FitnessFixtureUITests.swift:35,48`.

- An absence check made with no wait passes when the element has simply not appeared yet. This is the same
  settled-state problem as test-gaps class A, from the other side: these tests cannot fail on a transient show, and
  some cannot fail on a late show either. The 34 `XCTAssertTrue(x.exists)` asserts are safer, since each follows a
  `waitForExistence` on an element that lands at the same time (test-gaps section 1).
- **Fix (one worker task).** Add `XCUIElement.waitForNonExistence(timeout:)`/`assertStaysAbsent(for: 1.0)` to
  `WorkoutsUITests/Support` (a predicate expectation, not a sleep). Replace each `XCTAssertFalse(… .exists)` that
  directly follows a tap or a launch. Proof: `./dev ui-test` for the touched suites.

## P2

### P2-1 Kit tests that depend on wall-clock time (fixed sleeps checked against a debounce or a gate)

`WorkoutsTests/LiveActivityControllerTests.swift:405,414,421` (300/400 ms against an 80 ms debounce),
`RestNotifierTests.swift:478-490`, `HealthEnrichmentServiceTests.swift:291,314,344,459`,
`Packages/WorkoutsKit/Tests/WorkoutsKitTests/CloudKitReadinessTests.swift:182-193` (3 × 500 ms).

- On a loaded host (`./dev ui-test` runs 3 simulators while `./dev test`/`kit` runs in worktrees), a 400 ms sleep can
  finish before the debounced task runs, which makes the test flaky. The `#expect(!finished)` after a 100 ms sleep
  (`HealthEnrichmentServiceTests.swift:291-292`) can never fail for the wrong reason, but it proves only "not finished
  in 100 ms". The `MediaStoreTests.swift:368-387` polling loops have no deadline, so a regression hangs the suite
  instead of failing it.
- **Fix (one worker task per file group).** Inject a `Clock` into `LiveActivityController`'s debounce and use a
  `TestClock`/manual clock in its tests. Elsewhere, replace the sleeps with the existing `waitUntilInFlight`-style gates
  or a bounded `until(_:timeout:)` helper. Give the `MediaStoreTests` loops a deadline. Proof: `./dev test
  LiveActivityControllerTests` and `./dev kit CloudKitReadinessTests`, 10 runs each under `stress -c 8` (or alongside a
  ui-test run).
