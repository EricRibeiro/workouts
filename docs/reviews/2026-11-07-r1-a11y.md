# Full review round 1: accessibility (2026-11-07)

Read-only. Scope: `Workouts/Features`, `Workouts/App`, the Live Activity (`WorkoutsLiveActivity/`), and the palette in
`Assets.xcassets/Colors`. I checked the settled positions first: JC82 (audits gate every screen; `.secondary` at 4.2–4.5:1
is Eric's call), JC110 (sticky band capped at 3 lines), JC12 (empty fields read "Empty").

**Method.** I read the source and computed contrast ratios for the asset colours (WCAG 2.x relative luminance). The
automated `AccessibilityAuditUITests` already covers labels, contrast and clipping on the main screens, so this review
looks for what audits cannot see: custom actions, announcements, state conveyed only by colour or haptics, and hit
targets inside composed rows. `./dev tree ActiveWorkoutCover` was started but sat waiting on the simulator pool for more
than 4 minutes, and I stopped it. I took no AX5 screenshots, so the Dynamic Type findings below come from the code
(fixed heights, line limits, `ViewThatFits`). I did not change the content size and did not touch the simulator's
displays or pose.

**What is already good.** Every icon button in scope has a label. Set fields report "Empty" instead of the placeholder,
and a refused check is announced. The rest ring carries its time in the label with `.updatesFrequently`. The Live
Activity uses static accessibility strings, so it cannot crash on encoding (`ActivityTimers.swift:49`). The exercise
chart has an `AXChartDescriptor`. Calendar days carry full-date labels. Star Celebration, exercise thumbnails and video
all honour Reduce Motion. Set rows stack into two lines at accessibility sizes, and the column header is dropped there.
Every colour in the palette used for text passes 4.5:1 where it is drawn (the kind letters on `okRow` are 4.68–5.17).

## P2

### A11Y-1 Rest end has no non-haptic signal for VoiceOver, and the over state reads "0:00"
- `Workouts/Features/ActiveWorkout/Rest/RestExpiryWatcher.swift:22-25`, `ResumeControl.swift:80-83`,
  `Rest/RestRingItem.swift:100,114`, `App/Notifications/RestNotifier.swift:315` (`willPresent` returns `[]`).
- Evidence: when a rest reaches 0 with the app in the foreground, the only signals are `.sensoryFeedback(.success)` and
  the ring turning green with a checkmark. The banner is suppressed. Nothing posts an announcement. The ring's label
  becomes "Rest timer, 0:00" during the grace period, which a VoiceOver user cannot tell apart from a rest about to end.
  The resume ring says "rest 0:00". The Live Activity does say "Rest over" (`DynamicIslandViews.swift:23`), so the app is
  the inconsistent one.
- Fix (one task): in `awaitRestExpiry`'s `onEnded` call sites, post
  `AccessibilityNotification.Announcement("Rest over")`. Have `RestRingItem.runningButton` and `ResumeRingButton.state`
  say "Rest over" instead of "0:00" when `remaining <= 0`. Add a unit test for the label strings.

### A11Y-2 The resume ring's "elapsed" label goes stale while no rest runs
- `Workouts/Features/ActiveWorkout/ResumeControl.swift:69-77,114,124`.
- Evidence: without a rest, the button is built once with `now: .now` and has no `TimelineView`. The comment says the
  elapsed time is "read when VoiceOver asks", but `accessibilityLabel("Resume workout, \(state)")` is computed at render
  time. VoiceOver therefore reads the elapsed time from the last re-render (for example "0:05 elapsed" twenty minutes
  later).
- Fix: give the idle label a `TimelineView(.periodic(by: 60))`, or label it "Resume workout, started at 7:58 PM" with
  `startedAt.formatted(time:)`, which is static and still true (the same pattern as `timerAccessibilityValue` in the
  Live Activity).

### A11Y-3 Keyboard − / + steps don't tell VoiceOver the new value or the step size
- `Workouts/Features/Shared/SetTable/SetKeyboardToolbar.swift:60-74`, `SetFieldCell.swift:76-79`.
- Evidence: the buttons are labelled "Decrease by one step" and "Increase by one step". The step (2.5 kg, 5 lb, 1 rep,
  5 s) is never spoken. After a press, VoiceOver stays on the button and does not read the field's new value, so a blind
  user must swipe back to the cell after every step. The cell itself has no `accessibilityAdjustableAction`, so swipe
  up/down cannot step it either.
- Fix (one task): add `.accessibilityAdjustableAction` to `SetFieldCell`, fed by the same `step` closure that `SetRow`
  passes through. After a toolbar step, post an announcement of the focused field's new value ("Weight 82.5 kilograms").
  Optionally put the step size in the toolbar labels ("Decrease by 2.5 kilograms") through `SetKeyboard`.

### A11Y-4 "Delete set" and block reorder may be unreachable with VoiceOver
- `Workouts/Features/Shared/SetTable/SetTable.swift:116-124` (swipe action and `.accessibilityAction(named: "Delete set")`
  on a `SetRow`) and `:58-62` (`.reorderable()` / `reorderContainer`).
- Evidence: `SetRow` is `.accessibilityElement(children: .contain)` (`SetRow.swift:65`). A custom action attached to a
  container that VoiceOver never focuses is not offered on its children (the kind button, the cells, the check). So
  "Delete set" is probably reachable only through the swipe gesture, and swipe actions outside a `List` are not
  automatically exposed as rotor actions. Block reorder is drag-only. Nothing in the code adds "Move up" / "Move down"
  actions, and the template editor and past editor depend on the same table. **Not verified on device:** the tree dump
  did not get a simulator.
- Fix (one task): move the "Delete set" action onto the check button and the kind button, the row's always-present
  elements. Add `accessibilityActions { Move up; Move down }` on the block's name button, calling the same `reorder`
  path. Prove it with an XCUITest that runs `element.perform(customAction:)` (or reads `customActions` in the tree dump).

### A11Y-5 Note controls under a block's name are shorter than 44 pt
- `Workouts/Features/Shared/SetTable/SetTableNotes.swift:34-46` (sticky band: footnote plus 4 pt vertical padding,
  about 26 pt tall for one line) and `:69-76` (note line: one footnote line, about 18 pt).
- Evidence: both became buttons in 7.8b (JC110) with no minimum height. The audit's hit-region check covers only
  standard controls. These are `.plain` buttons around `Text`, and they sit right above the column header and the first
  set row. A missed tap there lands on the row, often mid-set.
- Fix: put `.frame(minHeight: 44)` (a scaled `touch` metric, as in `SetRow`) on the content shape of both buttons only,
  keeping the visual padding. One snapshot re-record.

### A11Y-6 Set field cells are 40 pt tall
- `Workouts/Features/Shared/SetTable/SetFieldCell.swift:29,54`.
- Evidence: `@ScaledMetric minHeight = 40.0`, while every other control in the row uses `touch = 44`
  (`SetRow.swift:28`). These are the most-tapped controls in the app.
- Fix: raise it to 44 (or reuse the row's `touch`). Re-record the SetRow and SetTable snapshots.
