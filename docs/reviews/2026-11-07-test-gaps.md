# Test gaps behind two device-found bugs (Fable, 2026-11-07)

Eric found two bugs on the Duo with the full suite green: the "Download all videos" bar restarting on every Settings
open (fixed in `9427456`), and the History detail pushed without its title and toolbar, which popped in ~0.5 s later
(fixed in `f1be1bd`). This is Fable's read-only analysis, unbiased by the orchestrator. PLAN Phase 7b holds the tasks.

## 1. Why each bug slipped through

### Bug 1: download progress restarting (`BulkVideoDownload` / `MediaStore.prefetch`)

- **The feature is off under every UI test and gallery launch.** `ExerciseMedia.swift:14`:
  `canStreamVideo = !arguments.contains("-uiTesting")`; line 17 builds `MediaStore(source: canStreamVideo ? … : nil)`.
  `BulkVideoDownload.start` guards on it, so `settings.downloadProgress` (`SettingsView.swift:233-243`) never appears
  under XCUITest. The `-videoCache empty|seeded` fixture only proves the turn-off alert. The wiring that restarted the
  pass (`SettingsView.swift:249` `.onChange(of: downloadAllVideos, initial: true)`, `RootView.swift:114-125` on
  scenePhase) had no test and could not have one.
- **Kit tests asserted the network side, not the observable progress.** Pre-fix `prefetchSkipsWhatIsAlreadyCached`
  asserted `source.requests` only; `prefetchFetchesAllSkipsFailuresAndReportsProgress` asserted ticks only for an
  all-uncached cache. Nothing asserted the first tick, or ticks on a second pass over the same cache.
- **App tests asserted terminal state.** `BulkVideoDownloadTests` checked `progress == nil` after completion and
  `isRunning`, never `progress` right after `start()`; the only repeat-invocation test was offline → online.
- **Scale.** Fixtures use 3-4 ids; with 1,029 the one-by-one recount takes seconds and is visible.

### Bug 2: detail pushed without title/toolbar (`WorkoutDetailView`)

- **UI tests waited past the transient.** `WorkoutDetailUITests.openFirstWorkout` waits 5 s for `history.detail`,
  which exists only after the `.task` load, and only then asserts the toolbar buttons. `HistoryListUITests
  .testMonthHeaderRowsAndDetail` has the same shape. All 39 bare `.exists` asserts follow a `waitForExistence` on
  something that lands at the same time or later: the suite proves settled states only.
- **The snapshot engine settles.** `SnapshotTesting.swift` `renderHosted` runs the run loop 0.5 s before drawing, the
  window the bug occupied, and no snapshot hosts a `NavigationStack` or bar.
- **The visual proof settles too.** `./dev shot` uses `duo screenshot --settle`: a screen that jumps once and then holds
  still is captured after the jump. Eric saw both bugs on a screen recording, the one proof mode nobody automates.
- JC92 had already codified the habit: "Its UI test asserts the effect, since XCUITest cannot see the spinner live."

Caveat on the new regression test (`HistoryListUITests.testDetailHasTitleAndToolbarFromTheFirstFrame`): `tap()` returns
after XCUITest's quiescence wait (~0.4-0.6 s of push animation), so the no-wait `.exists` catches a slower load but could
pass a ~300 ms delay on a fast simulator. Good, not yet deterministic (fixed by the latency seam).

## 2. Bug classes

- **A. First-frame / transient state**: what a screen shows between push/appear and the arrival of async state (title,
  toolbar, placeholders, layout shift). The suite asserts the fixed point, never the initial state.
- **B. Re-entrancy of background work**: `start()`/`resume()` fired by `onChange(initial: true)`/scenePhase; the initial
  value of observable state on the Nth invocation; progress invariants (starts at what is done, monotonic, hidden when
  complete).
- **C. Features disabled by the harness**: eleven `-uiTesting` gates in three kinds (off, isolation, seam; section 6). Under
  an "off" gate, green means "off", not "correct".
- **D. Fixture scale** (minor; it hides A and B).

## 3. Recommendations, ranked by value per cost

1. **Progress-model invariant tests in the kit** (~1 h, no flakiness). In `MediaStoreTests`, one parameterised
   `@Test(arguments:)` over cache {none, partial, all} × {first, second pass} via `ProgressTicks`: first tick ≥ cached
   count, non-decreasing, constant total, no ticks when nothing is pending, a second pass over an unchanged cache fetches
   and ticks nothing. Checklist line: every `progress:` closure gets a test recording all ticks including the first, plus
   a second-pass case.
2. **A DEBUG latency seam for async loaders + first-frame UI tests** (~half a day; low flakiness once forced; +~5 s per
   test). `#if DEBUG` `-slowLoads <ms>` honoured in `WorkoutStatsReader.loadWorkoutDetail`, the History dashboard summary
   and ExerciseDetail's loads. Test: launch with `-slowLoads 3000`, tap, assert title and `workoutDetail.edit` exist and
   `history.detail` does not, then wait for content. Helper `assertChromeImmediately(title:buttons:)` in
   `XCUIApplication+Waiting`, applied to WorkoutDetail, ExerciseDetail, TemplatePreview, PastEditor.
3. **Screen-level snapshot of the loading frame with a chrome-stability check** (~half a day; moderate setup risk; +~3 s).
   `SnapshotWorkoutDetailTests` hosting `NavigationStack { WorkoutDetailView(workoutID:) }` (`.hosted(height:)`) twice:
   loader held (the seam, or an environment-injected never-resolving loader) and loaded. Record both; add
   `Snapshot.assertSameChrome(loading, loaded)` comparing the top ~120 px. Catches pop-in and the content shift without
   timing. Risk: hosted `NavigationStack` teardown; fallback `.hostedFitting` with inline title mode.
4. **A fixture `MediaSource` instead of the media `-uiTesting` gate; audit the other gates** (~half a day; keep to one UI
   test). DEBUG `FixtureMediaSource` (`-mediaSource fixture[:delayMs]`) writing tiny files; `-videoCache partial:<n>`
   seeding n catalog ids. One `SettingsUITests` test: open Settings, read "n of M" (n = seeded), close, reopen, value
   never decreased. Proves the wiring rec. 1 cannot. Separately (30 min): list what each `-uiTesting` gate hides, marked
   "fixture exists" or "manual-only"; Live Activity and Health gates are legitimate.
5. **Second-invocation tests for every `@Observable` controller with start/resume** (near zero cost). `start()` tested on
   the second call after a completed and after a cancelled first, asserting the initial observable state. Applies to
   `RestNotifier`, `HealthEnrichmentService.appBecameActive` throttling, Live Activity start.
6. **`./dev shot --burst` for reviewers** (~1-2 h in `Tools/duo`). Lit-panel captures every ~100 ms for 1.5 s after
   launch or an injected tap, tiled into one PNG. A proof artifact for design review, not an assertion; `--settle` stays
   for steady-state proofs.
7. **A written rule, not a lint** (10 min). DECISIONS.md and the `design-review` state inventory: chrome
   (`navigationTitle`, `toolbar`, `searchable`) sits on the outermost view of a pushed screen and takes synchronously
   available values (the `@Query` row, the pushed id), never inside a loaded-state branch; loading is a named state in
   the inventory and must be rendered (rec. 3).

## 4. What not to automate

- Sub-second timing assertions through XCUITest without the latency seam (nondeterministic; would erode the gate).
- Frame-by-frame analysis of recordings or perceptual jump thresholds; assert chrome identity between frames instead.
- Real CloudKit downloads or 1,029-id fixtures; rec. 1 is scale-independent and rec. 4 covers wiring.
- A blanket "no `-uiTesting` gates" rule; the Health and Live Activity gates protect the simulators.
- Auto-exploring every gallery entry under `-slowLoads`; only the four pushed screens.

Suggested order: 1, 5 and 7 first; 2 (3 depends on its seam); 3; 4 at the next media change; 6 with the `Tools/duo` stream.

## 5. Checklist (for every new test or reviewed change)

- Every `progress:` closure gets a test recording all ticks, including the first, plus a second-pass case (7b.1).
- Every `@Observable` controller with `start()`/`resume()` is tested on the second call, after a completed and after a
  cancelled first, asserting the observable state right after the call (7b.2).
- Every pushed screen gets a first-frame chrome check: title and toolbar present while its content is still loading (7b.4;
  rule in DECISIONS → Pushed-screen chrome).
- A `-uiTesting` gate that turns a feature off means that feature's UI test proves "off", not "correct": name the fixture
  or mark it manual-only (7b.6).

## 6. `-uiTesting` gates

Every `"-uiTesting"` check under `Workouts/` (PLAN 7b.6; line numbers as of 2026-11-09). Three kinds: **off** (a feature
is turned off, so green means "off", not "correct"), **isolation** (the check keeps runs independent and hides no
feature) and **seam** (test-only machinery turned ON, so the UI suite drives it and the feature behind it is proven).
