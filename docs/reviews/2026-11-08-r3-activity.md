## c57429a threading fix: complete

- Both `UNUserNotificationCenterDelegate` methods are the completion-handler variants, `nonisolated`, and call the handler
  inside `Task { @MainActor in … }` (`RestNotifier.swift:333-358`). No `async` delegate variant is left anywhere in the app
  or extension: there are no other `completionHandler`s and no other delegates in `Workouts/`, `Shared/` or
  `WorkoutsLiveActivity/`.
- `UNUserNotificationCenter.add`'s completion (`:82-89`) only logs and leaves the `nonisolated static` group. It touches no
  main-actor state, so any thread is fine.
- `flush()`'s `notify` closure is explicitly `@Sendable` (`:111`). The `DispatchQueue.async` bodies in
  `SystemNotificationCenter` and `SystemLiveActivityProvider` are `@Sendable`, so they are nonisolated and only touch
  `nonisolated static` or `nonisolated var @Sendable` members.
- The intents hop through `ActivityIntentRouter.runOnMain` (`@MainActor`) before touching the handler. The observation
  `onChange` callbacks only enqueue a `Task { @MainActor … }`.

## Consistency of Skip / +30 s / Done (checked, fine)

- The notification fires only at the rest's end, so its Skip and +30 s always act on an over rest. Warm, the over rest is
  still in the model: +30 restarts from now (`RestTimer.adjust`). Cold, `resume()` has already cleared it:
  `extendOrRestart` starts 30 s from now. The result is the same either way. The Live Activity hides Skip and +30 once it
  is stale, so it never sends them on an over rest.
- The Live Activity's Done uses the set ID from its last render. `check` does nothing for a set that is already checked or
  gone, so a stale double tap cannot uncheck anything.
- After every background action, `syncNow` + `flush` push the notification and the Live Activity before the intent or
  response returns. The later debounced pass that follows is deduplicated (`isSame`) or replaces the request with the same
  fire date.
- Relaunch: `resume()` clears an expired rest. `observe` then removes the pending and delivered notification. The first
  reconcile adopts or ends leftover activities and updates the adopted one.

## Findings

### P2

**A3-1. With the cover closed, the end of a rest is silent on any pushed screen.** Files:
`Workouts/Features/ActiveWorkout/ResumeControl.swift:72-79` (the expiry watcher lives in the resume ring's toolbar item),
applied only at `HistoryView.swift:57`, `ExercisesView.swift:108` and `WorkoutView.swift:104`; `RestNotifier.swift:338-339`
(`willPresent` returns `[]`).
- **Who watches the rest.** While the app is in the foreground, the system banner and sound are always suppressed. The
  only things that play the success haptic, post the VoiceOver "Rest over" and forget the over rest are:
  - `RestExpiryWatcher`, on the cover;
  - the `.task` on `ResumeRingButton`, which exists only as a toolbar item of the three tab roots.
- **Why a pushed screen has no watcher.** Toolbar items do not inherit on push, and the `ResumeControl` doc says exactly
  that. A screen pushed on History or Exercises (workout detail, exercise detail, records) has no resume ring, so its task
  is gone: the root's item leaves the bar and its task is cancelled.
- **Scenario.** Check a set (a 2:00 rest starts), minimise, open History, then a past workout to compare.
- **What goes wrong.** At 0:00 there is no banner, no sound, no haptic and no announcement. The over rest is also never
  forgotten while the person stays there, so the Live Activity sits stale and "Rest over" until they pop back to a root.
- **Fix direction.** Host one expiry watcher at the root, gated on `!navigation.isWorkoutCoverOnScreen`, for example on
  `RootView`'s `TabView`, instead of in the toolbar item. Or apply `.resumeControl()` on the pushed destinations as well.
  Either way, keep exactly one watcher alive at a time so the haptic does not play twice.

### P3

**A3-2. A debounced sync can be cut off by suspension.** Files: `RestNotifier.swift:254-265`,
`LiveActivityController.swift:195-206`, `RootView.swift:114-117`.
- **The gap.** A foreground change waits 300 ms of quiet before it reaches the notification center and ActivityKit.
  Nothing flushes when the scene goes to the background (`.background` and `.inactive` only call `commitTypedValues`).
- **Scenario.** Tap a set's check and lock the phone at once. The schedule and the Live Activity update depend on the
  app getting more than 300 ms of background run time.
- **Impact.** It usually does, so this is not a crash or a common failure. If it does not, no rest-end notification is
  armed and the Live Activity shows no rest.
- **Fix direction.** In `scenePhase` → `.background`, run `await restNotifier.syncNow()` and
  `await activityController.syncNow()` inside a short `beginBackgroundTask`, through an environment closure or the intent
  handler's `flush()`.

**A3-3. The fallback on a store failure reads `Activity.activities` on the main thread.** File:
`Workouts/App/WorkoutsApp.swift:216-221`.
- **The code.** `endLiveActivities()` is `Task { for activity in Activity<…>.activities … }`. With default MainActor
  isolation, that Task runs on main, so the synchronous `chronod` round trip happens on the main thread.
- **Why it matters.** It is the same class of stall the provider moved off main (JC80). It runs right after
  `WorkoutsApp.init` when the container fails to open, which is also a launch path.
- **Fix direction.** Reuse `SystemLiveActivityProvider().existingActivities()` and `end(...)`.

### NIT

- **Repeated `chronod` round trips after a dismissal.** File: `LiveActivityController.swift:271-273`. Once the person has
  dismissed the activity, every reconcile for that workout still calls `endAll`, which runs
  `existingActivities()` → `chronod`, before the `dismissedWorkouts` check returns. Checking `dismissedWorkouts` before
  `endAll` saves the call when no other activity is held. It is only a cost, not wrong behaviour.
