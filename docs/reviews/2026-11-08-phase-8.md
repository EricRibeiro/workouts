## Verified (no finding)

- **Schema and CloudKit rules (question 2).** Walked every model in `SchemaV2`: all non-optional attributes have defaults, no
  `.unique`, every relationship is optional with an inverse (`Workout.template` ↔ `Template.workouts`, `WorkoutExercise.workout`
  ↔ `Workout.exercises`, `WorkoutSet.workoutExercise`, `Template.folder` ↔ `TemplateFolder.templates`,
  `TemplateExercise.template`, `TemplateSet.templateExercise`), delete rules are cascade or nullify, to-many arrays are always
  sorted by `position` before use (CloudKit keeps no order). `StickyNote` is absent from `SchemaV2.models`, which is what the flag
  fed to `initializeCloudKitSchema`, so `CD_StickyNote` was never created. The JSON `Data?` blobs are small (heart-rate points,
  zones, `HealthWorkoutDetails` without a route for strength workouts) and the mirror moves large `Data` to assets anyway.
  Nothing in V2 blocks additive changes. `./dev kit CloudKit` passes.
- **Engine reload path otherwise (question 1).** `reloadPrevious` clears `previousCache`/`previousLoaded` and reloads from the
  store on every merge, so Previous follows a workout finished elsewhere. `loadPrevious` tie-breaks equal starts (R2-03 fixed).
  `liveWorkout` guards every engine derivation (rest timer, activity state, notification plan). Both devices compute the same
  settlement (`plan` sorts by `startedAt` then id). The remote-change tests mutate through a second `ModelContext` on the same
  container, the right stand-in for a merge. `./dev kit RemoteChange` passes.
- **DEBUG flag (question 3).** The call (`WorkoutsApp.swift:89`) and the definition (`:355`) are both inside `#if DEBUG`
  blocks, so a Release build has no code path to it. `Task.detached(priority: .utility)` keeps the synchronous
  `initializeCloudKitSchema` round trips off the main thread even under the app target's `SWIFT_DEFAULT_ACTOR_ISOLATION =
  MainActor` (`project.xcproj:133`); the recorded run finished with "CloudKit schema initialized in Development", which it could
  not have done on a blocked main actor. `loadPersistentStores` calls back synchronously for a non-async description, so the
  continuation resumes exactly once. Errors reach the unified log with `privacy: .public`, which the runbook reads.
- **Push plumbing (question 4).** `aps-environment` (entitlements) plus `UIBackgroundModes` = `remote-notification` (Info.plist,
  merged with the generated plist as `CFBundleURLTypes` already is) plus the existing iCloud/CloudKit entitlement is the complete
  set Apple documents for `NSPersistentCloudKitContainer`; the mirror registers its own database subscription and needs no app
  delegate method. The `development` value is what a development-signed archive needs; `xcodebuild -exportArchive` with
  `method app-store-connect` re-signs with the distribution profile and rewrites it to `production`. `./dev testflight` passes
  `-allowProvisioningUpdates`, which registers the Push Notifications capability on the App ID; the upload of 202611090336
  succeeding is the proof the profile carried the entitlement.
- **`./dev ck-schema` token flow (question 5).** `CK_TOKEN_REF` holds the `op://` reference, not the value; `op run` resolves it
  only in the child's environment and masks it in output; `cktool` reads `CLOUDKIT_MANAGEMENT_TOKEN` from the environment
  (`man cktool`: "read from the CLOUDKIT_MANAGEMENT_TOKEN environment variable, the local store config file ~/.config/cktool or
  the login keychain, in that order"). `set +x` is forced at entry, `die` prints the reference only, the `op run -- true` probe
  separates a vault failure from a cktool failure, `comm -23` gets both inputs through `sort`, `diff` returns 1 while Production
  lacks a type and 0 otherwise, and the `DEVELOPMENT_TEAM` grep matches `project.xcproj:281`. `cmd_clean` removes
  `.build/cloudkit`.
- **Docs (question 6).** `docs/cloudkit.md` matches the code: Debug/Development vs TestFlight/Production, the flag's name and
  log line, `./dev run -- …` pass-through (`dev:727-730`), the `ck-schema` verbs and exit code, the `CKAccountStatusNoAccount`
  note, the 8.3 import rule (match by id, newer `updatedAt` wins). DECISIONS "Data and sync" and PLAN 8.1/8.3 agree with
  `WorkoutsApp.swift` and `Schema.swift`; JC126-JC128 describe what landed. Only P8-08's three lines are off.

## Not filed (checked, accepted)

- Two devices adopting the same in-progress workout and logging into it at once (the "workout started elsewhere appears" rule):
  by design since C-11 c, and the only way one device can see the other's running workout.
- `resume()` from the handler right after `finish()` can adopt another device's in-progress workout while the cover is still
  animating away (`lastShown`); cosmetic and two-device only.
- The observer also hears the throwaway schema-init store's coordinator (`object: nil`); harmless, DEBUG only.
- Importing the same JSON on two devices before they sync would duplicate rows by `id` (no unique constraints under CloudKit, the
  importer only sees its local store); there is one device, and the runbook's import step is done.
- `reloadCustom` throwing skips `reloadAfterRemoteChange` but the generation still bumps; the next change retries.
- `CloudKitReadinessTests`' `eventually` poller (R2-02) is unchanged; both suites passed alone in well under a second.

## Verdict

**Ship as is for the one-device setup; fix P8-01 before a second device signs in.** Nothing in this round loses data on a single
phone: the schema is CloudKit-clean and now frozen correctly, the DEBUG flag cannot reach Release, the push entitlements are the
documented set and the upload proved them, and the token never leaves `op run`'s child environment. The two-device path is where
it is not yet right: P8-01 is a one-line fetch bug that lets a newer workout on the other device finish or delete the one being
logged here within a second of the merge, P8-02 is the policy behind it (settle stale rows only), and P8-03 closes the
render-a-deleted-model window P-01 left in the views. Do those three as one worker task, then P8-04 (filter the app's own saves
out of the handler) before the sync is used daily; P8-05 to P8-08 are a docs-and-nits pass at leisure.
