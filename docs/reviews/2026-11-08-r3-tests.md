## P2

### P2-1 UI tests do not pin Dynamic Type or appearance, so a pool sim left at an accessibility size changes every UI run
- `WorkoutsUITests/Support/XCUIApplication+Launch.swift:14-15`: `launchedForTesting` adds only `-uiTesting` and the
  caller's arguments. No `-UIPreferredContentSizeCategoryName`, no appearance. `dev` does not reset the sim's
  `content_size`/`appearance` before `test`/`ui-test` either (no `simctl ui` call in `dev`).
- Six tests skip the helper and build `XCUIApplication()` themselves, so a default added there would not reach them:
  `HealthKitIntegrationUITests.swift:18`, `PerfDriverUITests.swift:23`, `SettingsUITests.swift:11,55`,
  `SmokeUITests.swift:12`, `TreeDumpUITests.swift:16`.
- Where the state leaks from: `.claude/skills/verify-ui/SKILL.md:124` tells agents to run
  `xcrun simctl ui <udid> content_size accessibility-extra-large` on their pool sim and set it back afterwards. If an
  agent forgets to set it back, the next `./dev ui-test` shard on that clone runs at AX-XL. Swipe counts then fall short
  and rows truncate or move. This is the recent false failure.
- It can also make a test pass while the feature is broken. `HealthEnrichmentUITests.swift:32-34` does 3 swipes and then
  checks `XCTAssertFalse(settings.health.enabled.exists)`. At AX-XL, 3 swipes may not reach the Health section. Its lazy
  Form row is then never created, so the absence check passes even if the section is wrongly shown.
- The launch argument does work under XCUITest: `AccessibilityAuditUITests.swift:368` passes
  `UICTContentSizeCategoryAccessibilityXL` this way. The skill's note about it not working applies only to `./dev shot`.
- **Fix.** `launchedForTesting` appends `-UIPreferredContentSizeCategoryName UICTContentSizeCategoryL`, plus a light
  appearance, unless `extraArguments` already sets them (AccessibilityAudit's `largeText` must still win, so don't append
  a second copy). Route the six direct `XCUIApplication()` launches through the same default, for example a
  `XCUIApplication.pinnedArguments` used by both. As a backstop, `dev` resets the sim with
  `simctl ui <udid> content_size large` and `appearance light` before `test`/`ui-test`. This is a UI setting, not a
  display toggle. Proof: set the sim to AX-XL, then run `./dev ui-test HealthEnrichmentUITests` and
  `./dev ui-test CustomExerciseUITests`; both should pass.

### P2-2 Rest-timing UI tests race app launch on the wall clock, and two can pass with the rest feature broken
- `Workouts/App/WorkoutsApp.swift:319` starts the sample rest (`engine.startRest(seconds:)`) while the app seeds data at
  launch. `launchedInActiveWorkout` then allows up to 15 s (`XCUIApplication+Launch.swift:57`) before the test does
  anything. Each test below needs its first step to land inside a window measured from launch:
  - `RestRingUITests.swift:114-121`: `-sampleRestSeconds 8`. The ring tap must open the running sheet (`rest.plus10`)
    before 8 s + 3 s grace. If launch plus the waits takes longer than about 11 s on a loaded shard, the ring opens the
    idle menu and `sheet.waitForExistence(5)` fails. That is a false failure.
  - `RestRingUITests.swift:151-162`: 10 s rest. The test must focus a set field and see `rest.keyboard.countdown` before
    the rest ends, or it fails falsely.
  - `ResumeControlUITests.swift:41-45`: 8 s rest. The minimise and the `resume.ring` wait (up to 10 s) can run past the
    rest.
- Two of them can pass while the feature is broken:
  - `RestRingUITests.swift:136-144` waits only for `label == 'Rest timer'`, the idle label. A rest that never started
    (or a ring that never shows running) reaches the same end state. There is no positive "running" anchor first.
  - `ResumeControlUITests.swift:45` checks `label.contains("rest ")`, which `"… rest over"` also matches. So the
    countdown state is not actually proven.
- **Deterministic replacement.** Start the rest when the test is ready, not at launch: drop `-sampleRestSeconds` for
  these tests and tap a ring preset after the screen is up. Then assert the running label (`rest.plus10`, `Rest 0:0x`),
  and only then wait for expiry with a generous bound. Better still, end the rest on command so no wall clock is
  involved: a `#if DEBUG`, `-uiTesting`-only trigger such as a debug link (the app already routes URLs, see
  `OpenWorkoutURLUITests`) that calls the engine's "expire now". The tests then assert running → trigger → grace →
  idle without timing. Proof: `./dev ui-test RestRingUITests` and `./dev ui-test ResumeControlUITests` while another
  shard runs.

### P2-3 Remaining "quiet window" sleeps in unit tests: they pass early under load, so they can pass with the feature broken
Each of these sleeps a fixed multiple of the debounce and then asserts that nothing else fired. A comment admits each one
"can only pass early". On a loaded host the extra callback can land after the sleep, so a coalescing or cancellation
regression goes green. The positive waits already use `eventually`/`CallSignal`. These are the leftovers from r1 P2-1,
which asked for an injected clock:

| Test | Lines | Time-based condition | Deterministic replacement |
|---|---|---|---|
| `WorkoutsTests/LiveActivityControllerTests.swift` `aBurstOfChangesUpdatesOnceWithTheFinalState` | 419, 427 | 240 ms sleep vs 80 ms debounce, then `contents.count == 2/3` | Inject `any Clock<Duration>` into `LiveActivityController` (`LiveActivityController.swift:162`, the `Task.sleep(for: debounce)` at :201). With a manual test clock: burst, `advance(by: debounce)`, await the reconcile signal, then `advance(by: debounce * 3)` and yield until no sleeper is pending. The count is then exact, with no wall time involved. |
| `WorkoutsTests/RestNotifierTests.swift` `aBurstOfChangesSchedulesOnceWithTheFinalPlan` | 604, 612 | same 240 ms vs 80 ms | Same clock injection into `RestNotifier`'s debounce. |
| `Packages/WorkoutsKit/Tests/WorkoutsKitTests/CloudKitReadinessTests.swift` `observerRunsOnceAfterABurstAndStopsWhenAsked` | 180, 188, 191 | 3 × 100 ms quiet windows: one after a burst, one after `stop()`, one after a post-stop post | Clock-injected `RemoteChangeObserver`. After `stop()`, assert that the observer holds no pending task (expose `isScheduled` for tests). That proves "stopped" structurally rather than by waiting. |
| `WorkoutsTests/HealthEnrichmentServiceTests.swift` `turnOffCancelsTheFollowUp` | 463 | `followUpDelay * 4` (200 ms), then `healthWorkoutID == nil` | Give the follow-up a handle the test can await (or inject the clock), then `await followUp.value` and assert it was cancelled and the source's lookup count stayed 1. Today a follow-up that is merely late passes. |

## P3

- **P3-1 Hand-rolled sleep polls (r1 P3-6, still open).** `HeaderRevealUITests.swift:18-25` (`Thread.sleep(0.1)` loop) and
  `SettingsUITests.swift:116-119` (`usleep(200_000)` until the toggle's value matches). Both are bounded, so neither is
  flaky. Replace them with `waitUntil` (`XCUIElement+Waiting.swift:97`) or an `XCTNSPredicateExpectation` on
  `value == %@` / `exists == %d`. `HeaderRevealUITests.swift:37`'s comment promises "not right away", but nothing asserts
  a minimum delay. Either assert `returned > 0.x` or drop the claim.
- **P3-2 "Dismissed" asserted with `XCTAssertFalse(x.waitForExistence(timeout: 2))` right after the dismiss tap.**
  `CustomExerciseUITests.swift:45,78,98,125,151,185` and `HistoryCalendarUITests.swift:79`. `waitForExistence` returns
  true at once if the sheet is still mid-dismiss on a slow shard. That is a false failure, and it reads as "stays absent"
  when the intent is "went away". Use `XCTAssertTrue(x.waitUntilGone(timeout: 5))`, as `HistoryCalendarUITests.swift:52`
  already does, then optionally `assertStaysAbsent`.
- **P3-3 Time-bounded absence with no settled signal.** `HealthEnrichmentUITests.swift:30`
  (`healthFitnessRow(app, timeout: 5)`) gives a wrongly triggered lookup 5 s to show calories. A slower one passes.
  Deterministic option: under `-uiTesting`, the fixture Health source exposes how many lookups ran (a debug-only
  accessibility value). Assert it is 0 after the row anchor. Absence asserts that still lack a settled anchor:
  `ExerciseDetailUITests.swift:22` (a toolbar `exerciseDetail.edit` checked the instant the name appears; use
  `assertStaysAbsent`), and `HealthEnrichmentUITests.swift:34` (see P2-1).
- **P3-4 Snapshots of the loaded state wait a fixed 3 s.** `SnapshotExerciseDetailTests.swift:39` passes `settle: 3 s` to
  `renderSettling` (`SnapshotTesting.swift:169`) for the loaded frame, and `SnapshotWorkoutDetailTests.swift:43` passes
  the same for `atSettle`. If the `.task` load has not landed under load, the "loaded" PNG shows the placeholder. That
  is a false failure. Replacement: keep drawing, as `renderSettled` does, until the content below the hero is stable
  across two draws and differs from the held (`slowLoads`) frame, with a deadline that records an issue.
- **P3-5 Gaps in the set-row snapshot batch.** `SnapshotSetRowTests.swift:15` takes `sampleRows.prefix(7)`, which drops
  row 8 (`SetRow.swift:434`, `canCheck: false`, the state whose check is refused). The batch has no row with
  `showsCheck: false` (the template editor's rows, `SetTableSources.swift:197,246`), none with `showsWeight: false`
  (bodyweight), and no checked row of a non-normal kind or of a duration. Only row 5 (normal, reps) is checked. Fix: use
  all 8 rows and add a second host of template-style rows (`showsCheck: false`) plus a checked warm-up and a checked
  duration row, then re-record. Also, `ExerciseDetailSnapshots`/`WorkoutDetailSnapshots` render only `large-light`
  (`SnapshotVariant.all[0]`), so the loading placeholders added in round 2d are not checked at AX3 or in dark.
